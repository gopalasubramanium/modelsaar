One address for your local AI.

Connect the AI apps you already use. ModelSaar sends each request to a suitable available model, chosen from the task, verified model capabilities and the limits you set.

Spend less time switching models and configuring apps. Keep control of where your requests run.

Several good models, one app at a time

Once you run more than one local model, every app needs its own model setting, and every task needs you to remember which model handles code, which one can read an image, which one is fast enough for chat. Change a model in Ollama and you change it in four places.

ModelSaar sits between your apps and your inference servers. Apps connect once, to one address, and ask for a virtual model called auto. For each request the gateway checks which of your deployments can actually do the job, picks one on evidence, forwards the request unchanged and records why.

Three things stay distinct:

Apps
Open WebUI, OpenCode, agents, scripts — anything that speaks the OpenAI Chat Completions API. They keep their own tools, memory and loops.
Inference backends
Ollama, vLLM, llama.cpp server and similar. They load weights and run on your hardware. ModelSaar does not replace them.
Models
The weights those backends serve, with their own licences. ModelSaar does not ship models or lower their hardware requirements.

Three steps to a first routed request

  1. Install ModelSaar

    macOS, Linux or WSL2. The one-line installer uses your uv or pipx if you have one, otherwise an isolated environment of its own (it can fetch a pinned uv for that; never sudo, never the system Python), and pins one candidate commit.

    Terminal
    curl -fsSL https://modelsaar.com/install.sh | sh

  2. Start the gateway

    The installer has already run modelsaar init: it found Ollama on 127.0.0.1:11434 (an inference server with at least one model must already be running), wrote a private config and keys, and listed the models it discovered. Now start the gateway and leave it running.

    Terminal
    modelsaar serve

    Installed from source instead? Run modelsaar init first (once; it refuses to overwrite an existing config), then modelsaar serve.

  3. Connect an app

    Point the app at the gateway and pick auto as the model. Print the API key in a terminal, then paste the printed line (it starts with msk_) into the app's key field:

    Terminal
    head -1 ~/.modelsaar/keys/api_keys
    Values to paste
    Base URL:  http://127.0.0.1:8484/v1
Model:     auto
API key:   msk_…  (the line printed by the command above)

    One command per app prints its exact settings: modelsaar client-config open-webui, modelsaar client-config opencode, modelsaar client-config openclaw or modelsaar client-config hermes.

Verify from a second terminal with modelsaar test: it first identifies the gateway on the configured port (an unrelated service there is reported as a collision and receives no key), lists the models the gateway advertises and sends one chat completion through auto, printing which deployment answered and the request id — the routing attribution that shows ModelSaar handled it. Full details, including Docker and remote hosts, in Get started.

Measured, not promised

In the accepted run of 2026-10-15 (four models on one machine, 32 held-out tasks, 400-token budget), automatic routing scored 30 of 32 and the strongest single model 29 of 32 — a difference the data cannot distinguish from zero — with a median end-to-end latency of 0.38 s against 3.44 s and zero capability violations, because the router sent almost every task to a resident fast model and the one image task to a vision-capable one. Two later runs on an upgraded runtime, with five and then all eight of the machine's models, matched the strongest single model exactly; in the eight-model run the router picked that model itself on every task because it was the one resident at the time. Routing overhead — the decision itself, separate from the response — stayed under 1 ms at p95 in all three runs.

Those are three runs on one machine with a small task set; the confidence intervals overlap, the later runs are not comparable to the first (different Ollama version), and no run isolates the effect of adding one model. Read the methodology, numbers and limitations, or regenerate every aggregate from the raw per-request records.

Practical questions

What hardware do I need?

Whatever your inference backend needs to run the models you want; ModelSaar adds a small Python process and no GPU requirement of its own. It has been run on a MacBook Air talking to an ASUS GX10 over a private network, and on a plain Linux container against a test backend.

Do I need models already?

Yes. ModelSaar never downloads models and never accepts model licences on your behalf. Pull them with your backend (for example ollama pull gemma4:e4b) first. modelsaar demo starts a clearly labelled simulated backend if you want to try the commands without any model.

Does it use the internet?

Not for routing. The gateway binds to loopback, talks only to the backend addresses you configure, sends no telemetry and never fetches remote media. The installer downloads the ModelSaar source from GitHub at a pinned commit, and your package tool downloads its Python dependencies.

What about cloud models my backend forwards to?

By default (locality_mode: local_only) deployments that Ollama marks as cloud-forwarded are excluded, even when a client asks for them by name. Set allow_remote deliberately if you want them; the decision record shows the locality evidence either way.

I only have one model.

Then auto uses that model whenever it qualifies for the request, and you still get one address, generated keys, a health check and a decision record. Adding a second model later changes nothing in your apps.

Which models are supported?

Any model your backend serves. Capabilities (tools, image input, strict JSON, streaming) are discovered from the backend and verified with short probes; a capability that is unknown never qualifies a model for a request that needs it. A small catalogue supplies optional quality hints that are labelled as priors until you measure.

What happens when nothing qualifies?

You get an HTTP 422 with the blocker for every deployment and a remedy — never a silently truncated history, a dropped image or a weakened schema.

What does it cost? What is the licence?

ModelSaar is free, Apache-2.0 licensed open source. Model weights keep their own licences, which you accept through your backend.

How do I update or uninstall?

Re-run the installer: it pins the newer candidate commit and keeps your config, keys and state. modelsaar uninstall removes only the files ModelSaar created and lists anything it left in place; then remove the package with your package tool. Details in Installation.

How do I see why a model was chosen?

Every response carries X-ModelSaar-Request-Id and X-ModelSaar-Deployment. modelsaar decisions lists recent decisions, modelsaar explain -m "…" dry-runs a request, and /admin/ui shows the status page. Records hold metadata only, never your prompts.

Try it on the models you already have

Python and a running backend are all you need for a first routed request. If something does not work, the issue templates ask for exactly the decision record and doctor output that make it fixable.
