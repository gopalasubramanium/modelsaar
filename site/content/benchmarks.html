Benchmarks and evidence

Does automatic routing help? The honest answer so far: on one recorded run it matched the best single model's score and did better on coverage, at the cost of higher tail latency. Everything on this page can be regenerated from files in the repository.

Method

modelsaar eval compares auto (live routing through the gateway) against policies that use the same requests, the same gateway and the same budgets:

  • fixed-strong and fixed-fast: the single deployment with the best success / lowest latency on a calibration split that is disjoint from the test split;
  • rules: a deterministic mapping that is given the gold task label and the catalogue's specialist tags — an advantage auto does not have;
  • random (seeded) as a floor and oracle (a task counts as solved if any deployment solved it) as an offline ceiling that is not available at runtime.

The task set is 47 original synthetic tasks (conversation, coding, agent/tools, math, extraction with strict schemas, summarisation, translation, RAG-style, decisions, image questions, a tool round trip, mixed-language and deliberately ambiguous prompts), split 15 calibration / 32 test with different templates. Scoring is executable or exact: numbers with tolerance, strict tool-call validation, JSON-schema checks, and Python tasks run inside an isolation sandbox (bubblewrap, macOS sandbox-exec or Docker) or skipped with the changed denominator reported. No LLM judge. Full definition: Evaluation and the fixture README.

Reading it. Automatic routing matched the strongest fixed model's observed task score (30 of 32 each), completed more requests (32 vs 31 — the image task the fixed model cannot take) and recorded fewer capability violations (0 vs 1). Its p95 end-to-end latency was higher ({{ '%.0f' % facts.live_eval()['rows'][0]['p95'] }} vs {{ '%.0f' % facts.live_eval()['rows'][1]['p95'] }} ms) because two requests went to a slower thinking model. The two policies differ on exactly two tasks: the image task (auto solved it) and one long transformation task that the same model answered correctly in the fixed sweep and incorrectly in the auto run — run-to-run variation at temperature 0, not a routing difference.

What it does not show. n = 32 and every 95 % confidence interval overlaps every other; equal point estimates do not establish equivalence, and nothing here shows general superiority. The 400-token budget systematically penalises the two thinking models (their reasoning counts against it), so the fixed model was also the one that happened to suit the budget; a matched larger budget has not been run. One machine, one runtime, three of eight available models, synthetic tasks.

Routing overhead — the time the gateway spends deciding, separate from response latency — was mean {{ facts.live_eval()['routing']['overhead_ms_mean'] }} ms, p95 {{ facts.live_eval()['routing']['overhead_ms_p95'] }} ms over the 32 auto requests, with the deterministic task label matching the gold label {{ '%.0f' % (facts.live_eval()['routing']['task_label_accuracy']*100) }} % of the time and the classifier disabled.

Raw evidence and reproduction

  • docs/live-runs/2026-10-11-gx10-hardening/: the report (eval-live.json), 173 sanitised per-request records (eval-live.json.records.jsonl: ids, status, latency, scorer detail — no prompts), probe outputs, decision records, the redacted configuration, model digests and a MANIFEST.md with every setting.
  • python scripts/eval_aggregate.py <records> <report> recomputes every aggregate from the records and exits non-zero on any difference (it matched).
  • Run your own: modelsaar eval --mode live --save-measurements --out eval.json (resumable with --checkpoint/--resume); the saved measurements then become routing evidence for your deployments.
  • An earlier run with the pre-review evaluator (lenient scorers) reported auto 0.875 vs fixed 0.906; it is kept as a historical record in the verification report and is not comparable.
