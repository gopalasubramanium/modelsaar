Get started

From nothing to a first request routed through auto. Two paths: the beginner path installs, configures and verifies in a few commands; the expert path is the same thing without the wrapper.

Status: ModelSaar is a development preview. No release has been tagged and no package is published, so every install path below pins the reviewed commit {{ facts.INSTALL_SHA[:12] }} of the {{ facts.INSTALL_BRANCH }} branch. Re-running the installer later moves you to the next reviewed commit.

Before you start

  • An inference backend with at least one model. Ollama is the first-class path: ollama serve running and a model pulled (for example ollama pull gemma4:e4b). Any OpenAI-compatible server (vLLM, llama.cpp server, LM Studio) also works; you will declare its models in the config. ModelSaar never downloads models and never accepts a model's licence for you.
  • Python 3.10 or newer, or the uv tool (which fetches a suitable Python itself). Check with python3 --version or uv --version.
  • macOS (Apple silicon or Intel), Linux, or Windows through WSL2. macOS arm64 and Linux x86_64 are the platforms the project has actually run on; native Windows is untested.
  • Hardware: whatever your backend needs for the models you chose. ModelSaar itself is a small Python process.

1. Install

Beginner path: one command

{{ cmd(facts.INSTALL_ONE_LINER) }}

The script is short and does only this: checks your platform and Python; installs the ModelSaar package at the pinned commit with uv tool install, pipx or python3 -m pip install --user (first one found; it does not install those tools for you); runs modelsaar init if you have no config yet (it looks for Ollama on 127.0.0.1:11434 and other documented loopback ports, writes ~/.modelsaar/config.yaml and private keys with mode 600); then starts a temporary gateway, sends one request through auto, stops it and prints the result with your next step. Existing config, keys and state are never overwritten; an occupied gateway port is reported, not fought over.

To read it before running it:

{{ cmd(facts.INSTALL_INSPECT) }}

Options are environment variables: MODELSAAR_ENDPOINT=http://host:port (backend other than local Ollama), MODELSAAR_PORT=8484, MODELSAAR_NO_CHECK=1 (skip the verification request), MODELSAAR_REF=<sha> (install a different commit — you take responsibility for it).

2. Configure and run

Before this step an inference server with at least one model must be running (for example ollama serve after ollama pull …); ModelSaar never downloads models.

If you used the one-line installer, modelsaar init has already run (the installer printed the models it discovered) — skip to modelsaar doctor. With uv, pipx, pip or a source checkout, run it once:

{{ cmd('modelsaar init', 'Finds Ollama on 127.0.0.1:11434 (or pass --endpoint URL --type ollama|openai_compatible), writes ~/.modelsaar/config.yaml and keys, discovers your models. Refuses to overwrite an existing config without --force; after the installer, do not run it again.') }} {{ cmd('modelsaar doctor', 'Reachability, assumed context lengths, unknown capabilities, cloud-forwarded aliases — with a remedy per warning.') }} {{ cmd('modelsaar serve', 'Starts the gateway at http://127.0.0.1:8484/v1 (loopback only). Leave it running; stop with Ctrl-C.') }}

Optional but recommended once: modelsaar probe --all verifies streaming, tool calling, JSON schema and image input on each model with short real requests (it uses your backend's compute). Run it while the gateway is up; the probes go through the gateway so they never collide with your own traffic.

Verify

{{ cmd(facts.FIRST_USE_CHECK, 'In a second terminal. Identifies the listener on the configured port (GET /healthz must answer the ModelSaar health contract before any key is sent), lists the models the gateway advertises and sends one chat completion through auto; prints the deployment that answered and the request id.') }}

If it prints an HTTP 422, no model qualified — the body says which blocker applies to each deployment and what to change. If it cannot connect, the gateway is not running on the configured port; the message says so. If something else is listening on that port, it says "not a ModelSaar gateway" and sends nothing: change server.port or stop the other service.

3. Connect an app

Any app that speaks the OpenAI Chat Completions API needs three values. First print the key in a terminal:

{{ cmd(facts.KEY_COMMAND, 'Prints one line starting with msk_. That printed line is the API key to paste into a GUI field; the command itself is shell syntax, not a key.') }} {{ cmd('Base URL: ' + facts.GATEWAY_URL + '\nModel: auto # or auto-fast, auto-code, auto-vision, or a concrete deployment id\nAPI key: ' + facts.KEY_PLACEHOLDER, lang='text') }}

Or let ModelSaar print the exact settings for your app — one command per app:

{{ facts.client_config_list_html() }}

--apply merges file-based configs with a backup and keeps the file's permissions. The key never leaves your machine unless you send it somewhere.

Addresses when the app is not on the same machine. 127.0.0.1 always means "the machine (or container) where the app runs". An Open WebUI container on the same host reaches the gateway at http://host.docker.internal:8484/v1; an app on another computer needs the gateway bound beyond loopback (server.host: 0.0.0.0 and security.allow_lan: true, with TLS or a private network in front — see Privacy). modelsaar client-config … --docker prints the container form.

One model only? auto uses it whenever it qualifies; nothing else changes. More models later expand its choices without touching the app.

Running it day to day

Keep it running
Run modelsaar serve under your service manager; a launchd plist and a systemd unit are in examples/. Docker Compose is documented in Installation (gateway only; models stay with your runtime).
Stop / restart
Ctrl-C in the terminal, or your service manager's stop/restart. Configuration changes need a restart; in-flight requests finish on the old config.
Update
Re-run the installer (it pins the newer reviewed commit), or with uv/pipx/pip re-run the install command with the new commit. Then modelsaar config validate and modelsaar doctor. Keys and state are untouched; evidence from an older evidence scheme is kept but not used until you re-probe.
Troubleshoot
modelsaar doctor first; then modelsaar decisions --limit 10 for the last routing records and modelsaar explain -m "…" [--tools --image --json-schema] to dry-run a request. More in Troubleshooting.
Uninstall
modelsaar uninstall removes only the files ModelSaar created under ~/.modelsaar (config, its backups, keys, state DB) and lists anything it left in place. Then uv tool uninstall modelsaar, pipx uninstall modelsaar or pip uninstall modelsaar. Models and client configurations are never touched; applied client configs have .bak-<timestamp> copies next to them.

What has actually been tested

The one-line installer and the uv/pip paths were executed in a clean environment on Linux (x86_64) and on macOS (arm64) against the pinned commit; the exact transcripts are linked from the verification report. WSL2 follows the Linux path and has not been executed by the project. Native Windows is not supported yet.
