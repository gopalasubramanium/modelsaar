Evaluation harness

Rendered from docs/evaluation.md at commit b9d69f7299ed. The repository file is authoritative.

modelsaar eval is an executable harness that compares auto against strong fixed policies on a compact, inspectable task set with executable or exact scoring. It reports per-category results with 95 % Wilson intervals, completion rate, capability violations, latency and routing overhead.

Task set

src/modelsaar/evaluation/fixtures/tasks.jsonl: 47 original synthetic tasks (Apache-2.0, no third-party data) across conversation, coding, agent/tools, math, extraction (strict schema), summarization, translation, RAG-style, decision, vision, a tool round trip, mixed-language and deliberately ambiguous prompts, plus a long-but-easy transformation. Splits: calib (15) and test (32) use different templates. Scorers: nonempty, contains, contains_any, json_schema (+field checks), tool_call (strict: non-empty id, expected name, JSON-object arguments that conform to the tool's declared parameter schema, contain every required parameter and the expected substrings), code_exec (a trusted runner executes the model code with its stdout captured, then the task harness with its stdout captured, and writes a result record keyed with a per-run nonce; the task passes only when that record says the harness completed and the harness output equals the expectation — text the model prints, including any "completion marker", is never evidence). code_exec runs only under bubblewrap (Linux; only the Python runtime and system libraries are visible), sandbox-exec (macOS; deny-by-default profile with runtime read roots — unsupported in this alpha pending verification: disabled unless MODELSAAR_MACOS_SANDBOX=verify, so on macOS code_exec tasks are skipped and the report says why) or Docker (--network none --read-only) with CPU/memory/output/time limits; without one of those the task is skipped and the report says so — there is no host-execution fallback. The sandbox is tested for writes, network, timeouts and reading a synthetic host file outside the work directory; it does not defend the evaluator against model code that targets the evaluator process itself. Scorer rules are versioned (SCORER_VERSION) and recorded in the report's conditions; checkpoint records (--checkpoint, --resume) are bound to the task content, the scorer version and request budgets, the routing configuration and the eligible deployment set (for routed policies: a new, removed or re-identified alternative re-runs the task) and the deployment fingerprint, and anything that no longer matches is re-run and counted under resume_rejected instead of being attributed to the new run. --probe runs the capability probes through the gateway's admission, one reservation per deployment; after an uncertain timeout the reservation is held and the remaining deployments are reported deferred rather than probed on top of work that may still be running. No LLM judge is used. See src/modelsaar/evaluation/fixtures/README.md for the exact rules.

Procedure

  1. Probe every local generative deployment (streaming, tools, json_object, json_schema, vision) so capability evidence is real, not declared.
  2. Sweep the calib split over every deployment → per-deployment quality/latency. This calibrates the fixed-strong (best calib success) and fixed-fast (lowest calib p50) baselines and, with --save-measurements, becomes routing evidence keyed by fingerprint.
  3. Sweep the test split over every deployment → per-deployment results and the oracle (a task counts as solvable if any deployment solved it; an offline upper bound, unavailable at runtime).
  4. Run auto live through the gateway on the test split (routing overhead measured per request from the decision record).
  5. Derive rules (deterministic specialist mapping that is given the gold category label, an advantage auto lacks) and random (seeded) from the test sweep.

All policies send identical requests through the same HTTP gateway with the same eligibility checks and budgets (temperature 0, max_tokens 400).

Running

modelsaar eval --mode simulated                 # no models needed; validates mechanics only
modelsaar eval --mode live --probe --save-measurements --out eval-$(date +%F).json

Live mode starts an in-process gateway from your config on a free port. Because that gateway's admission cannot coordinate with another instance using the same backends, the run refuses to start while a gateway listens on the configured port unless you pass --allow-concurrent. Long runs are resumable: --checkpoint PATH (default <out>.records.jsonl with --out) appends one sanitised record per request (ids, status, latency, scorer detail — never prompts), and --resume skips recorded tasks whose deployment fingerprint is unchanged. The report records exact deployments (model, parameter size, quantization, runtime, context, fingerprint, endpoint), the conditions (max_tokens, temperature, seed, scorer version, git commit, sandbox backend, dataset revision), date, sample counts and every request's outcome. scripts/live_verify.sh wraps probes, wire-level client checks and this evaluation into one resumable command.

Acceptance targets for a reference configuration

Define before measuring; the harness reports against them.

metric target
capability violations (422 for requests a deployment could serve) under auto 0
completion rate under auto ≥ fixed-strong
overall success under auto ≥ fixed-strong − 0.05 (never materially worse than the best single model)
routing overhead (deterministic path) p95 < 5 ms; with classifier < classifier.timeout_s
classifier timeouts < 5 % of consulted requests

Reporting rules

  • Report per-category results with uncertainty; never a single universal "% better".
  • If auto cannot beat a good fixed policy on your hardware, say so; the benefits may then be capability coverage (tools/vision/context across models), flexibility, or installation — and the simple mode (request a concrete deployment id) remains.
  • Adaptive learning, bandits and online exploration are not part of 0.1 (roadmap).
