Installation, upgrade, rollback, uninstall

Rendered from docs/installation.md at commit 1d8656394ca7. The repository file is authoritative.

Native (recommended)

Prerequisites: Python 3.10+ (python3 --version), git, and a running inference server with at least one model (e.g. ollama serve + ollama pull gemma4:e4b). ModelSaar never downloads models.

git clone <repository> modelsaar && cd modelsaar
python3 -m venv .venv && . .venv/bin/activate
pip install -e .            # editable install from source; `pip install .` for a plain install
modelsaar init              # discovers Ollama on 127.0.0.1:11434 or pass --endpoint/--type
modelsaar doctor
modelsaar serve

With uv: uv venv && . .venv/bin/activate && uv pip install -e . (or uv tool install . to get a global modelsaar command).

modelsaar init is for a first installation: it refuses to overwrite an existing config.yaml (--force replaces it; keys and state are kept). If you installed with the website's one-line installer, init has already run — continue with modelsaar serve and, in another terminal, modelsaar test. modelsaar test first identifies the listener on the configured port (unauthenticated GET /healthz must return the ModelSaar health contract) and sends the API key only to a ModelSaar gateway; an unrelated service on that port is reported as a collision.

Files created by init (default ~/.modelsaar, override with MODELSAAR_HOME or --config):

~/.modelsaar/config.yaml      versioned configuration (version: 1), mode 600
~/.modelsaar/keys/api_keys    generated inference key(s), one per line, mode 600
~/.modelsaar/keys/admin_key   generated admin key, mode 600
~/.modelsaar/state/modelsaar.db   probe evidence, measurements, decision log (metadata only)

No PyPI package or container image is published; the commands above are the supported path.

Configuration essentials

version: 1
server: { host: 127.0.0.1, port: 8484 }
security: { allow_lan: false, locality_mode: local_only, log_prompts: false }
resource_pools:
  - { id: local-machine, kind: unified, max_concurrent: 1 }    # one inference at a time on this box
backends:
  - { id: ollama, type: ollama, base_url: http://127.0.0.1:11434, resource_pool: local-machine }
  # - id: vllm
  #   type: openai_compatible
  #   base_url: http://127.0.0.1:8000/v1
  #   resource_pool: local-machine
  #   models:                                   # declare what discovery cannot tell
  #     - name: Qwen/Qwen3.8-27B
  #       context_length: 65536
  #       capabilities: { tools: supported, json_schema: supported }
  #       tags: [code]
deployments:                                     # operator overrides with visible provenance
  - { backend: ollama, model: "qwen3.8:27b", context_length: 32768, tags: [code] }
routing:
  default_profile: quality
  classifier: { enabled: false }                 # optional local classifier (see routing.md)
affinity: { mode: session, session_headers: [X-ModelSaar-Session, X-OpenWebUI-Chat-Id] }
embeddings:
  - { alias: docs-index, deployments: ["ollama/embeddinggemma-2:latest"], dimensions: 768 }

modelsaar config validate|show|example. Reload by restarting serve (in-flight requests keep their snapshot).

Docker Compose (optional)

docker compose up --build builds a local image from Dockerfile (no published image). The container needs to reach your inference server on the host:

host OS backend URL inside the container notes
macOS / Windows (Docker Desktop) http://host.docker.internal:11434 works out of the box
Linux http://host.docker.internal:11434 requires extra_hosts: ["host.docker.internal:host-gateway"] (already in docker-compose.yml)
WSL2 http://host.docker.internal:11434 if Ollama runs in Windows; http://<wsl-ip>:11434 if Ollama runs inside WSL Ollama must listen beyond loopback (OLLAMA_HOST=0.0.0.0) for a container to reach it

Inside a container the gateway binds 0.0.0.0 (security.allow_lan: true in examples/config.docker.yaml) so Docker can publish the port; publish it to 127.0.0.1:8484 only unless you intend LAN exposure. The container provides the gateway only; model execution and hardware acceleration remain with your runtime on the host.

Upgrade

cd modelsaar && git pull && pip install -e .      # or uv pip install -e .
modelsaar config validate                          # fails loudly if the config version is unsupported
modelsaar config migrate                           # applies migrations when a newer config version exists
modelsaar doctor

Config files carry version: 1. A build that cannot read your version refuses to start with a message instead of guessing. Keys and state are untouched by upgrades.

Rollback

git checkout <previous tag> then pip install -e .. Configuration is forward-compatible within a major version; if a migration changed your file, restore config.yaml.bak-* written by migrate.

Service management (optional)

Run modelsaar serve under your service manager. A minimal launchd plist (macOS) and systemd unit (Linux) are in examples/. Remove the unit/plist to stop auto-starting.

The one-line installer (curl -fsSL https://modelsaar.com/install.sh | sh)

The website's installer installs the pinned commit from its GitHub source archive (no git needed) into an isolated environment and never into the operating system's Python — it does not use sudo, pip install --user, --break-system-packages or the EXTERNALLY-MANAGED marker. In order: your uv (uv tool install) or pipx if present; otherwise a user-owned virtual environment created by your Python 3.10+ at ~/.local/share/modelsaar/envs/<commit>; and if that Python cannot create one (missing python3-venv/ensurepip, or an older Python) it downloads one pinned, checksum-verified official uv release binary for your platform into ~/.local/share/modelsaar/uv and lets it create the environment (uv fetches a Python of its own, 3.10–3.13, into ~/.local/share/modelsaar/python only when no Python 3.10+ exists). ~/.local/share/modelsaar/envs/current points at the active environment and ~/.local/bin/modelsaar is linked to it unless that name is already taken by something else, in which case the installer prints the full path to use. The runtime directory (MODELSAAR_RUNTIME_DIR) is separate from the configuration directory (MODELSAAR_HOME); re-running the installer reuses a complete environment and replaces one only after the new one has installed. Exit codes: 0 installed + configured + routed check passed (or skipped), 1 package or configuration not set up, 2 package and configuration in place but the routing check failed.

Uninstall

modelsaar uninstall        # removes ModelSaar's own files under ~/.modelsaar after confirmation
pip uninstall modelsaar    # or: uv tool uninstall modelsaar / pipx uninstall modelsaar
# installed by the website's one-line installer into its own environment:
rm -rf ~/.local/share/modelsaar      # the environment, and the uv/Python it downloaded, if any
rm ~/.local/bin/modelsaar            # only if it is the link the installer created

Uninstall removes only the files ModelSaar created (config.yaml and its backups, its key files, its state database) and then the directories if they are empty; anything else under ~/.modelsaar is left in place and listed. It refuses to operate through symlinked keys/ or state/ directories. It never touches models in your runtime or client configuration files. Client configs changed with client-config --apply have .bak-<timestamp> copies next to them (same permission bits as the original); restore those to undo the change.

Evidence scheme and upgrades

The state database records an evidence scheme (currently 2). Probes and measurements written under an older scheme (0.1.0: fingerprints without endpoint/identity, lenient evaluator) are kept for audit but never used for routing; modelsaar doctor reports how many such rows exist and the remedy (modelsaar probe --all, modelsaar eval --mode live --save-measurements). scripts/install-check.sh reproduces a clean wheel install, the loopback default, private key files and this migration.

Container first start

docker compose up with an empty volume works without a pre-created key: the image's command is modelsaar keys ensure && exec modelsaar serve, which creates /data/keys/* once (never rotating existing keys) and leaves the read-only config.yaml mount untouched. scripts/compose-smoke.sh checks exactly this (empty volume, non-root user, read-only config, keys unchanged across a restart) and runs in CI.
