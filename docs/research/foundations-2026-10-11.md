## 4. Other relevant components (one paragraph each)

**llama-swap** (https://github.com/mostlygeek/llama-swap) — MIT, Go, "zero dependencies", "one binary, one configuration file". Latest release v252 (31 Aug 2026; v251 23 Aug; v250 14 Aug). "Reliable model swapping for any local OpenAI/Anthropic compatible server - llama.cpp, vllm, etc." Routes **by model name only**: reads `model`, starts/stops the matching upstream (ttl unload, `matrix` DSL for concurrent models, `aliases`, `profiles`, `useModelName`, `stripParams/setParams`). Exposes `/v1/chat/completions`, `/v1/completions`, `/v1/responses`, `/v1/embeddings`, `/v1/models`, `/v1/audio/*`, `/v1/images/*`, `/v1/rerank`, Anthropic `/v1/messages` + `count_tokens`, llama-server `/infill`, `/props`, management `/running`, `/health`, `/metrics`. Fully local. No content-based or capability-based selection. Highly relevant as a *lifecycle/VRAM* layer beneath a router, or as a protocol-surface reference. [V] 2026-10-11, https://github.com/mostlygeek/llama-swap ; /releases.

**Open WebUI** (https://github.com/open-webui/open-webui) — licence is a BSD-3-derived "Open WebUI License" with a branding clause: "strictly prohibited from altering, removing, obscuring, or replacing any 'Open WebUI' branding" unless ≤50 users/30 days or enterprise licence. Its "Arena Model" "randomly selects from a pool of available models", collects thumbs up/down and ranks models with "an Elo rating system"; topic tags re-rank per domain. **No automatic content-based routing**: "Model selection is either random (Arena Model) or manual." Useful as a *client* and as a feedback source, not as a router. [V] https://docs.openwebui.com/features/evaluation/ ; https://github.com/open-webui/open-webui/blob/main/LICENSE.

**LocalAI** (https://github.com/mudler/LocalAI) — MIT, Go core, 47.8k stars, latest release v4.9.0 (20 Aug 2026). "Drop-in API compatibility: OpenAI, Anthropic, and ElevenLabs APIs", "drop-in Ollama API" (4.2.0), "60+ backends" installed as OCI images on demand, "Automatic Backend Detection". Distributed mode ("PostgreSQL + NATS") with "VRAM-aware smart routing + autoscaling" (4.1.0), "per-request replica routing" (4.3.0), "prefix-cache-aware routing". Routing is infrastructure-level (replica/VRAM), not task-quality model selection. Heavy footprint (full inference server). Relevant as a backend ModelSaar should discover. [V] https://github.com/mudler/LocalAI ; /releases.

**Ollama** — see §5. Native: `/api/tags`, `/api/show` (with `capabilities`), `/api/ps` (`size_vram`, `expires_at`, `context_length`), `/api/version`; OpenAI-compatible subset incl. `/v1/responses` (v0.13.3+); Anthropic-compatible endpoint also documented (`/api/anthropic-compatibility`). Latest release v0.40.2 (08 Oct 2026). No routing of its own beyond model-name dispatch and cloud offload. [V] https://github.com/ollama/ollama/releases ; https://docs.ollama.com/api/introduction.

**aurelio-labs/semantic-router** (https://github.com/aurelio-labs/semantic-router) — MIT, Python, 3.9k stars, latest tag v0.2.0.dev1 (24 Aug). Utterance-embedding route layer; encoders OpenAI, Cohere, HuggingFace, FastEmbed; indexes local/Pinecone/Qdrant. "If wanting to use a fully local version of semantic router you can use `HuggingFaceEncoder` and `LlamaCppLLM`" (`pip install "semantic-router[local]"`). It is a *library*, not a gateway; it could supply the intent-matching primitive in a Python gateway with a local encoder. [V] https://github.com/aurelio-labs/semantic-router ; /releases.

**Portkey Gateway** (https://github.com/Portkey-AI/gateway) — MIT, TypeScript/Node, 13.0k stars, latest release v1.15.2 (12 Jan). "tiny footprint (122kb)", `npx @portkey-ai/gateway` on :8787. Routing = weighted load balancing, fallbacks, retries, "conditional routing", guardrails. Ollama listed as provider (streaming). No capability/semantic selection; Responses API not mentioned on README. [V] https://github.com/Portkey-AI/gateway ; /releases.

**Bifrost** (https://github.com/maximhq/bifrost) — Apache-2.0, Go, 7.5k stars, latest "Bifrost HTTP v1.6.7" (30 Jul). `npx -y @maximhq/bifrost` or `docker run maximhq/bifrost`; "<100 µs overhead at 5k RPS". Load balancing, fallbacks, semantic caching, governance; drop-in `/openai`, `/anthropic`, `/genai` endpoints; Ollama listed. README states "enterprise deployments unlock advanced capabilities including adaptive load balancing, clustering, guardrails, MCP gateway" — the OSS/enterprise boundary is unclear. No capability-aware model selection. [V] https://github.com/maximhq/bifrost ; /releases.

**Not Diamond** (https://github.com/Not-Diamond/notdiamond-python) — cloud router ("automatically determines which LLM is best-suited"), requires `NOTDIAMOND_API_KEY`; **repo archived by owner on 2025-12-11**, 91 stars. Not local. [V] GitHub page.

**aisuite** (https://github.com/andrewyng/aisuite) — MIT, Python, 16.1k stars; "Simple, unified interface to multiple Generative AI providers"; provider prefix `<provider>:<model>`; Ollama supported; no fallback/load-balance/semantic routing documented. Client library, not a gateway. [V] GitHub page.

## 5. Ollama API facts (verified)

**OpenAI compatibility** — https://docs.ollama.com/api/openai-compatibility (and `.md` variant), checked 2026-10-11:

## Implications for ModelSaar (recommendation)

**What the evidence says about each "adapt" path**

1. *Extend vLLM Semantic Router.* It is the only candidate that does real capability/intent-aware model selection and already speaks Chat Completions + Responses + Anthropic Messages with tool/strict-schema translation (an 18-cell verified matrix). But its footprint contradicts ModelSaar's "simple installation, no mandatory cloud dependency, local-first" goals: Docker/Podman **and Envoy** are mandatory in the shipped stack, backend discovery is static YAML (no Ollama `/api/tags` or `/api/show` capability probing), it needs GBs of classifier/embedding models (307M encoders × many signals, 0.6B embedder, ~1.2 GB ONNX each), and optional Milvus/Redis for cache/memory. It also has no embeddings endpoint. Its licence (Apache-2.0) is fine. It is pre-1.0 with fast-moving config (0.3 → 0.4 in four months). Verdict: too heavy to be ModelSaar's base; worth borrowing its *design* (signals → decisions, replay/explainability, fail-closed field translation).

2. *Extend LiteLLM.* Mature, MIT core, Ollama provider support, huge protocol surface. But: the ordinary Router is load-balance/fallback only; capability awareness is limited to context window and region (no tools/vision filtering); there is **no Ollama model discovery**; "Auto Routing" is **beta** (shipped Jul 2026, "config keys ... can still change"), defaults to a heuristic complexity scorer and its examples lean on hosted services (Claude Haiku classifier, Voyage embeddings, TypeSafe-hosted Jev), with custom classifier rubrics gated as "Enterprise custom-classifier capability"; the Adaptive Router is beta and needs Postgres. The `proxy` extra pulls 31 packages including `litellm-enterprise` (proprietary licence) and cloud SDKs (boto3, azure-*). Verdict: a plausible *upstream* for cloud fallbacks, but adapting its routing core to capability-verified local selection would mean fighting the design and the licence split.

3. *Extend RouteLLM.* Apache-2.0 but effectively unmaintained (last release Jul 2024), strictly **two-model strong/weak**, the recommended `mf`/`sw_ranking` routers call OpenAI `text-embedding-3-small` on every request, and it depends on torch/transformers. Verdict: not a base; its calibration/eval approach (threshold vs. % strong calls, MT-Bench/MMLU/GSM8K evals) is the useful idea.

4. *Compose from llama-swap / Portkey / Bifrost / aurelio semantic-router.* llama-swap (MIT, single Go binary, zero deps, broad endpoint coverage incl. Responses and Anthropic Messages) already solves process lifecycle/VRAM swapping for llama.cpp/vLLM and is actively released (weekly). Portkey/Bifrost are load-balancers with cloud-centric feature sets and (Bifrost) an unclear enterprise boundary; neither selects by capability. aurelio semantic-router can run fully local (`HuggingFaceEncoder`) and gives an intent-matching primitive if ModelSaar is Python.

**Recommendation: implement a small, purpose-built gateway and compose, do not extend.**

Concretely:
- Build ModelSaar as a single-binary/single-process OpenAI-compatible gateway (Go or Python; Go matches llama-swap/Bifrost precedent and gives a zero-dependency install) exposing `/v1/chat/completions`, `/v1/responses` (stateless, like Ollama), `/v1/embeddings`, `/v1/models`, streaming, tool-call pass-through; add Anthropic `/v1/messages` later via the same translation discipline vllm-sr documents (fail closed on untranslatable fields).
- Make **discovery and capability verification** the differentiator none of the above has: poll Ollama `/api/tags` + `/api/show` (`capabilities`: completion/tools/vision/embedding/thinking/insert; `details.parameter_size`, `quantization_level`; `model_info["<arch>.context_length"]`), `/api/ps` (`size_vram`, `expires_at`, `context_length`) and `/api/version`; detect cloud-forwarding models via `-cloud`/`:cloud` names and `remote_model`/`remote_host`; for vLLM read `/v1/models`, `/version`, `/tokenize`, and infer tool support from server flags (`--enable-auto-tool-choice` + parser) with a live probe, since Ollama ignores `tool_choice` and vLLM's `hf` parser rejects named/required.
- Route on **verified capabilities + hardware fit + measured performance** (a deterministic scorer: required capability filter → context fit → VRAM/loaded-state preference from `/api/ps` → measured TTFT/TPS → optional small local intent classifier). Keep any learned/semantic layer optional and local (e.g. an aurelio-style route layer with a local encoder, or a distilled 307M-class encoder as vllm-sr does), never a hard dependency on a cloud embedding API.
- Delegate what others do well: llama-swap (or LocalAI) for model process lifecycle on llama.cpp/vLLM; LiteLLM or Bifrost as an *optional* downstream for cloud providers; Open WebUI Arena/feedback as a signal source.
- Ship routing explainability (per-request decision record, as vllm-sr's Replay does) and an offline eval harness (RouteLLM-style calibration on a small local benchmark) from day one, because none of the local-capable options provide both.
- Licence: Apache-2.0 or MIT for ModelSaar; avoid vendoring anything from `litellm/enterprise` or Bifrost enterprise paths.

Footprint target that the evidence supports as achievable: one binary or `pip install` with <15 deps, no Docker/Envoy/Redis/Postgres, no mandatory model download, first useful route within one minute of pointing it at an Ollama or vLLM endpoint.
