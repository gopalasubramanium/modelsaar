Benchmarks and evidence

Does automatic routing help? Three recorded runs in October 2026 show the same held-out task score as the strongest single model — never a statistically established advantage — with lower latency when the router picks a resident fast model and no capability violations. Nothing more is claimed. Every number on this page is read from the report files in the repository at build time and can be regenerated from the per-request records.

Method

modelsaar eval compares auto (live routing through the gateway) against policies that use the same requests, the same gateway and the same budgets:

  • fixed-strong and fixed-fast: the single deployment with the best success / lowest latency on a calibration split that is disjoint from the test split;
  • rules: a deterministic mapping that is given the gold task label and the catalogue's specialist tags — an advantage auto does not have;
  • random (seeded) as a floor and oracle (a task counts as solved if any deployment solved it) as an offline ceiling that is not available at runtime.

The task set is 47 original synthetic tasks (conversation, coding, agent/tools, math, extraction with strict schemas, summarisation, translation, RAG-style, decisions, image questions, a tool round trip, mixed-language and deliberately ambiguous prompts), split 15 calibration / 32 test with different templates. Scoring is executable or exact: numbers with tolerance, strict tool-call validation, JSON-schema checks, and Python tasks run inside an isolation sandbox (bubblewrap, macOS sandbox-exec or Docker) or skipped with the changed denominator reported. No LLM judge. Full definition: Evaluation and the fixture README.

All three runs below used one frozen contract: gateway and evaluator at commit cf56cdd3416d, scorer 2026.10.12-3, temperature 0, max_tokens 400, seed 7, the live classifier disabled, code isolation sandbox-exec, the harness on a MacBook Air driving an ASUS GX10's Ollama over a private network. Success is the share of the 32 held-out tasks scored correct; completion is the share that returned HTTP 200; a violation is a 422 for a request some deployment could have served; latencies are end-to-end per request and include the network path equally for every policy.

Accepted run — 2026-10-15, four models, Ollama 0.40.3

Deployments: qwen3.6:latest (35.5B Q4_K_M), gemma4:31b (31.3B Q4_K_M), qwen3.8:latest (27.3B Q4_K_M), qwen3-coder:latest (30.5B Q4_K_M). Calibration chose qwen3.8:latest as fixed-strong and qwen3-coder:latest as fixed-fast. This is the owner-accepted Stage B Pass 1 result; an earlier attempt the same day was compromised by a laptop sleep during the run and is preserved, labelled as such, in the same folder.

The difference is not statistically established: 3 tasks passed only under automatic routing and 2 only under the fixed model, and the paired 95 % confidence interval includes zero. Automatic routing selected qwen3-coder:latest on 31 of 32 tasks and the vision-capable fixed-strong model on the one image task, which is why its median latency was 0.38 s against 3.44 s for fixed-strong, with zero capability violations against one for fixed-fast.

Second run — 2026-10-16, five models, Ollama 0.40.5 (cross-runtime)

The same four deployments plus qwen3-coder-next (80B MoE, the largest model on the machine). Reading it. Automatic routing selected qwen3.8:latest — the fixed-strong model — on all 32 tasks, so the two policies share every outcome (30 of 32 each) and the same median latency (3.00 s). Among the three candidates with equal measured quality the choice was decided by which model happened to be resident when the routed phase began: here the thinking model was and the fast coder was not, the mirror image of the first two runs. That is the router's residency weight doing what it is designed to do, and it is also the main limit of this benchmark design — see below. The slow vision-capable model muse-glimmer failed its live vision probe although it declares vision, and the router excluded it from image tasks accordingly.

What these runs do not show

  • n = 32 held-out tasks per run; every 95 % confidence interval overlaps every other; equal point estimates do not establish equivalence and nothing here shows general superiority of routing over a well-chosen single model.
  • Residency decides ties. With measured quality equal across the top candidates, the router picks whatever is resident; in the harness that is an artefact of which per-model sweep ran last. The runs do not measure routing under realistic residency churn.
  • Cross-runtime. The accepted run used Ollama 0.40.3, the later two 0.40.5; differences between them are confounded by the runtime, a re-created tag and the pool, all at once.
  • Budget. The 400-token budget systematically penalises thinking models (their reasoning counts against it): dozens of their failures are suspected budget terminations, unproven because the harness records no finish reason; no run was repeated at a larger budget.
  • One machine, one gateway revision, synthetic tasks, the production gateway never in the loop.

Routing overhead — the time the gateway spends deciding, separate from end-to-end response latency — was p95 0.47 ms, 0.57 ms and 0.52 ms over the 32 routed requests of the three runs, with the deterministic task label matching the gold label 84 % of the time and the classifier disabled.

The optional classifier — one configuration tested, kept off. On 2026-10-25 the plan's classifier comparison ran once with qwen3.8:latest as the classifier at a 2000 ms timeout, consulted only on ambiguous requests. That configuration failed its predeclared timeout criteria: 38 of 38 classifier calls timed out (6 of 6 under routing), so it never produced a label, and routing overhead was p95 2003.52 ms against a 2000 ms limit. Routing reproduced the accepted run's outcomes exactly (30 of 32 against 30), so the decision rule keeps this configuration off. This is not a causal on-versus-off comparison: the only usable off reference is the accepted run on a different Ollama version (cross-runtime), and the same-session off twin was compromised by a backend health flap (209 of its requests refused) and is preserved as such. It says nothing about classifiers in general — a non-thinking classifier model or a longer timeout would be a different experiment. Evidence: docs/live-runs/2026-10-25-gx10-classifier-comparison/.

Raw evidence and reproduction

  • docs/live-runs/2026-10-15-gx10-stage-b-pass1/, docs/live-runs/2026-10-16-gx10-stage-b-pass2/ and docs/live-runs/2026-10-24-gx10-stage-c/: each holds the report, the sanitised per-request records (ids, status, latency, scorer detail — no prompts), the stored routing decisions, probe outputs, model identities, the launcher console and a MANIFEST.md with every setting, deviation and hash.
  • python scripts/eval_aggregate.py <records> <report> recomputes every aggregate from the records and exits non-zero on any difference (it matched for all three runs).
  • Run your own: modelsaar eval --mode live --save-measurements --out eval.json (resumable with --checkpoint/--resume); the saved measurements then become routing evidence for your deployments.
  • Earlier runs are kept as history and are not comparable: the three-model run of 2026-10-11 under scorer 2026.10.11-2 and Ollama 0.32.13 (docs/live-runs/2026-10-11-gx10-hardening/) and, before it, a run with the pre-review lenient scorers (verification report).
