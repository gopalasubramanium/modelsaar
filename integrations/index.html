Apps (clients)

Any application that speaks the OpenAI Chat Completions API can use ModelSaar: set the base URL to the gateway, the API key to your generated key, and the model to auto (or another alias). The clients below have generated, documented configuration; each page says exactly what was verified.

Open WebUI

Admin Panel → Connections → OpenAI connection with URL http://127.0.0.1:8484/v1 (from a container: http://host.docker.internal:8484/v1). Models are auto-listed from /v1/models. ENABLE_FORWARD_USER_INFO_HEADERS or a custom X-ModelSaar-Session header keeps a chat on one model; TASK_MODEL_EXTERNAL=auto-fast sends background tasks to the fast alias.

OpenCode

A provider entry using @ai-sdk/openai-compatible with the aliases as models; both the V1 (provider) and V2 (providers) config schemas are generated, and --apply refuses to mix them.

OpenClaw

Provider configuration pointing at the gateway; the client keeps its own tool execution and permissions.

Hermes Agent

YAML provider/model settings merged into Hermes's config with a backup; file permissions are preserved.

Scripts and SDKs

Any OpenAI SDK with base_url and api_key set; response headers carry the request id and the deployment that answered.

Inference backends

Ollama

First-class. Discovery uses Ollama's native API (/api/tags, /api/show for capabilities, context and template, /api/ps for what is loaded, /api/version); inference goes through Ollama's OpenAI-compatible layer so its tool-call semantics are preserved exactly. Cloud-forwarded models (remote_model) are detected and excluded under local_only. Known limits of that layer (tool_choice=required/named, remote image URLs, logit_bias, n, logprobs) are rejected with blockers instead of being altered. The served context of an unloaded model is unknown to Ollama's API; ModelSaar assumes 4096 unless the Modelfile, /api/ps or an override says otherwise, and doctor warns about every assumption. Verified live with Ollama 0.32.13 and eight models.

OpenAI-compatible servers (vLLM, llama.cpp server, LM Studio, …)

Supported through a generic adapter: /models for discovery, declared models in the config for what discovery cannot tell (context length, capabilities, tags, memory estimate, identity), vLLM's /tokenize for token counts when present. Tested against the fixture implementation only; not yet run against a real vLLM or llama.cpp server. Declare a locality for such a backend consciously — a generic endpoint exposes no evidence of where it runs.

Several backends and hosts

Backends can live on other machines (the recorded runs talk to a GX10 over a private network). Each backend declares a resource pool so concurrency and memory budgets are counted where the work happens. Routing across hosts is not scheduling: ModelSaar does not load, unload or move models.

Not supported yet

  • Responses API and Anthropic Messages (explicit 501).
  • Audio and video inputs, multimodal embeddings, OCR and guardrail pipelines (requests carrying them are rejected before dispatch).
  • Managed model loading/unloading, cascades, ensembles, learned routing policies.
  • Native Windows (use WSL2).

See the roadmap for what is planned and Extending for how to add a backend or client with its own tests.
